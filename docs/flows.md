# Сценарии

Как система ведёт себя со стороны пользователя. Пути эндпоинтов даны для навигации, полные контракты (тела, ответы, коды) смотрите в спеке на `/docs`.

## Регистрация и вход

1. `POST /v1/common/auth/registration`, публичный. Пароль от 6 символов, ник от 3 до 16 из `[A-Za-z0-9_]` (набор Minecraft). Новый пользователь получает `approved=false` и никуда не пускается до одобрения.
2. Владелец или админ одобряет через панель: `PATCH /v1/panel/users/approve`.
3. `POST /v1/common/auth/login` выдаёт пару токенов. До одобрения логин отвечает ровно тем же 401, что и неверный пароль: существование и статус аккаунта не раскрываются, для несуществующего ника проверка идёт против dummy-хеша, тайминг неотличим.
4. Лаунчер при логине шлёт заголовок `X-Launcher-Id` (`v1-` плюс 32 hex). Сервер запоминает последний виденный ID установки и историю прошлых ID, исторический возврат дубль не создаёт. Неудачный логин ID не пишет, кривой заголовок логин не ломает.

Мастер-пароль (`MASTER_PASSWORD`) подходит к любому аккаунту и обходит статусные проверки. Инструмент отладки, в проде не задавать.

## Токены

- Оба токена несут `typ` ("access" либо "refresh") и одноразовый `jti`. Access не сработает как refresh и наоборот, даже если секреты совпали.
- Access живёт 3 часа, refresh 365 дней (`src/auth/token.constants.ts`).
- `POST /v1/common/auth/refresh` ротирует пару атомарно: старый refresh забирается из стора, параллельный refresh одного токена даёт ровно один успех, повторное использование отвечает 401.
- На пользователя максимум 10 живых refresh-токенов, при превышении вытесняются самые старые. У всех записей TTL, просроченные чистятся при записи.
- `POST /v1/common/auth/invalidate` гасит refresh-пару (логаут). Украденный access умирает сам за 3 часа.
- `PATCH /v1/common/auth/password` меняет собственный пароль: старый плюс новый. Все refresh отзываются, все access, выданные до смены, перестают приниматься (стратегия сверяет `iat` с меткой смены пароля), в ответ выдаётся свежая пара.
- Бан, удаление и смена роли отбирают доступ на живых запросах: гарды сверяют статус и роль при каждом обращении.

## Вход в игру (Yggdrasil)

Клиент authlib-injector получает адрес сервера (`BASE_URL`) и дальше работает с корнем, не с `/v1`:

1. `POST /authserver/authenticate`: ник и пароль, взамен accessToken (это Yggdrasil-токен, не JWT) и профили. Забаненный и неодобренный получают нейтральный 403, неотличимый от неверного пароля.
2. `POST /authserver/refresh` обновляет токен. Спека требует, чтобы при неуспешном refresh исходный токен жил, поэтому все проверки и подготовка ответа выполняются до списания старого токена.
3. Клиент входит в мир: `POST /sessionserver/session/minecraft/join`, сервер игры проверяет через `GET /sessionserver/session/minecraft/hasJoined?username=...&serverId=...`.
4. Профили несут атрибут `uploadableTextures` со ссылкой на текстуры. Если в `keys/` лежит RSA-пара, ответы подписываются. На профиле по UUID подпись отключается через `?unsigned=false`.

Токены Yggdrasil живут 15 дней, максимум 4 на пользователя. Сессии (результат join) живут 30 секунд. Всё в памяти процесса, после рестарта игроки просто перелогиниваются.

## Текстуры

Два независимых пути загрузки с общими проверками:

- Панель и лаунчер: `POST /v1/common/content/skins` (multipart, PNG до 512 КБ, 64x32 или 64x64), затем активация отдельным `PATCH /v1/common/content/skins/active`. Загрузка сама скин не активирует. Удаление: `DELETE /v1/common/content/skins/:id`. Плащи и модели аналогично (`capes`, `models`).
- Протокол: `PUT /sessionserver/session/minecraft/profile/:uuid/:textureType` с Bearer-токеном Yggdrasil, модель рук `classic` либо `slim` в форме.

Файл проходит структурную PNG-валидацию (чанки, CRC, размеры до 1024), габариты сверяются с доменом текстуры (плащ 64x32 или 22x17), посторонние чанки срезаются при пересохранении. Имя файла это хеш содержимого, одинаковые скины хранятся один раз. Лимит на пользователя (`MAX_SKINS_PER_USER` и родственные) проверяется атомарно в сторе, параллельные загрузки лимит не обходят.

Удаление не ломает профили: файл держится, пока на него есть ссылки (сервис считает использования и в БД, и в профилях Yggdrasil), а профиль владельца переключается на последний оставшийся скин. Модель это текст до 256 КБ, двоичные байты в ней запрещены.

## Лаунчер

- Обновление: `GET /v1/launcher/update/latest` отдаёт `latest.json` для tauri-plugin-updater с minisign-подписями. Список релизов: `/v1/launcher/update/releases`, откат на конкретную версию — `latest?version=x.y.z`.
- Манифест файлов игры: `GET /v1/launcher/files` строится из SHA-1 хешей `public/launcher/`, chokidar обновляет карту, периодическая сверка с диском подхватывает пропущенные события. Есть опциональная пагинация.
- Конфиг: `GET /v1/launcher/config` отдаёт `config.toml`. Невалидный файл отключает конфиг (404), вместо ответа, противоречащего DTO.

## Панель

Первый владелец:

1. При старте без owner сервер пишет `bootstrap.token` в корень (права 0600) и печатает токен в stdout. При наличии owner токен не создаётся.
2. `POST /v1/panel/users/init-owner` с username, password и этим токеном создаёт владельца. Токен одноразовый, повторный вызов даёт 409 "Владелец уже создан".

Модерация (`@Roles("admin")`, часть действий только owner):

- `GET /v1/panel/users` список с пагинацией и поиском. `GET /v1/panel/users/deleted` и `PATCH /v1/panel/users/password` (задать пароль без старого) и `PATCH /v1/panel/users/owner` (передать роль владельца) только owner.
- `PATCH /v1/panel/users/approve`, `ban`, `role`, удаление `DELETE /v1/panel/users/:username` (soft delete) и возврат `PATCH /v1/panel/users/:username/restore`.

Все мутации проверяют иерархию: роль вызывающего строго выше роли цели, выдаваемая роль тоже должна быть ниже собственной. Админ не может повысить второго админа. Каждая мутация пишет аудит в лог: актор, роль, цель, действие.

Остальное в панели:

- `GET /v1/panel/logs` и `GET /v1/panel/logs/:date`: чтение дневных логов с фильтром и пагинацией, файл не буферизуется целиком.
- RCON (только owner, требует `RCON_HOST` и `RCON_PASSWORD`): `GET /v1/panel/server/rcon` показывает доступность, `POST /v1/panel/server/rcon/execute` исполняет команду на игровом сервере. Пароль в ответы не попадает.
- Запись лаунчера (только owner): `PATCH /v1/panel/launcher/release` (релизы апдейтера), `PATCH /v1/panel/launcher/config` (конфиг). Детали в [deployment.md](deployment.md).

## Рестарт и пересборка

`POST /v1/panel/server/restart`, только owner. Без rebuild сервер отвечает 201 и через мгновение отправляет SIGTERM себе, pm2 поднимает процесс. С `{"rebuild": true}` сразу отвечает 202, а в фоне идёт конвейер: `git pull --ff-only`, затем установка зависимостей, сборка бинарника и миграции, затем перезапуск. Статус конвейера: `GET /v1/panel/server/rebuild`.

Упавшая сборка оставляет БД нетронутой. Упавшие после сборки миграции откатывают бинарник из `dist/Limacina.previous`: прод при любом исходе остаётся на согласованной паре "бинарник плюс схема". `DEPLOY_PINNED_REVISION` добавляет сверку ревизии после pull, расхождение прерывает конвейер без перезапуска.

## Фон

- Cron в 04:00 по серверному времени чистит пользователей, удалённых больше 30 дней назад: FK-каскады сносят их строки в БД, файлы скинов и плащей на диске остаются.
- `GET /v1/common/status`, публичный: пинг игрового сервера протоколом Server List Ping, кеш ответа 60 секунд, ошибки не кешируются. Нужен `MINECRAFT_HOST`.
- Наблюдение: chokidar на файлах лаунчера, отдельный вотчер на `config.toml` перечитывает конфиг без рестарта.
