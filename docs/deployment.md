# Эксплуатация

## Прод-запуск

Чистый сервер: PostgreSQL 14+, Bun 1.4.2+, pm2 7+. Пошаговый первый запуск (база, `.env`, ключи, миграции, сборка, `init-owner`) — в [README](../README.md). MariaDB поддержана SQL-сторами и интеграционными тестами, но миграции в репозитории postgres-only: новое окружение на MariaDB командами проекта с нуля не поднимается.

`bun run build` собирает самодостаточный бинарник `dist/Limacina`. Флаги сборки не упрощать: `NODE_ENV=production` зашивается в бинарь на этапе компиляции, без него в проде ломается ветка логирования. Бинарник запускается из корня проекта: `.env`, `public/`, `keys/`, `logs/`, `config.toml` читаются относительно рабочей директории.

Прод живёт под pm2 (`ecosystem.config.js`): fork-режим, autorestart, рестарт при памяти выше 1G. Защита от рестарт-лупа: в лимит рестартов идут только падения с аптаймом короче 10 секунд, осознанный рестарт здорового процесса (кнопка из панели) в лимит не попадает.

```bash
bun run pm2:start      # старт
bun run pm2:status     # статус
bun run pm2:logs       # хвост логов
bun run pm2:restart    # рестарт (в том числе после пересборки)
```

Логи: `logs/YYYY-MM-DD.log`, JSON-строки, тот же поток дублируется в stdout. 5xx и транспортные ошибки на уровне error, отказы мутаций и security-события на warn. Ротацию делает внешний logrotate: файл пересоздаётся сам в течение минуты. На тот же день можно смотреть из панели: `GET /v1/panel/logs/:date`.

Автозапуск после перезагрузки машины: `pm2 startup` (выполнить выведенную команду), затем `pm2 save`.

## Обновление сервера

Два пути.

Вручную: `git pull --ff-only`, `bun install --frozen-lockfile`, `bun run build`, `bun run migrate:up`, `bun run pm2:restart`. Сборка идёт до миграций: упавшая сборка оставляет БД нетронутой. Ручной путь не создаёт `dist/Limacina.previous`, поэтому перед сборкой сохраните текущий бинарник, если нужен откат.

Через панель: `POST /v1/panel/server/restart` с `{"rebuild": true}`, только owner. Сервер в фоне выполняет конвейер: `git pull --ff-only`, `bun install --frozen-lockfile`, сборку, миграции, затем перезапускает себя. У каждого шага свой таймаут, вывод шагов в ответ не попадает, только в лог. Статус конвейера: `GET /v1/panel/server/rebuild` (в процессе, последняя ошибка, ревизия до и после).

Что делает конвейер безопасным:

- Сборка строго до миграций. Упавшая сборка оставляет БД нетронутой, старый бинарник продолжает работать.
- Перед сборкой бинарник копируется в `dist/Limacina.previous`. Упавшие после сборки миграции откатывают бинарь из копии: в любой момент прод держит согласованную пару "бинарь плюс схема".
- `DEPLOY_PINNED_REVISION` (полный SHA) сверяется с ревизией после pull, чужая ревизия в ветке прерывает конвейер без перезапуска.
- `git reset` на рабочем каталоге не делается: повторный rebuild просто продолжит с той ревизии, на которой остановился.

Зависимости обновлять точечно (`bun update <пакет>` или точный пин), лок-файл `bun.lock` коммитится и в rebuild ставится с `--frozen-lockfile`.

## Обновление панели

```bash
bun run panel:deploy          # последняя ветка
bun run panel:deploy v1.2.0   # тег или SHA для отката
```

Скрипт клонирует репозиторий панели в `tmp/panel-admin` (переопределяется `PANEL_REPO_DIR`), ставит зависимости, собирает и атомарно подменяет `public/panel`. Рестарт не нужен: маршрут `/panel` зарегистрирован на старте, статика отдаётся по свежим файлам. Прерванный посреди подмены деплой чинится сам: при следующем запуске и при старте сервера бэкап восстанавливается на место. Параллельные деплои сериализуются локом, второй ждёт или отвечает ошибкой через 10 секунд.

## Релизы лаунчера

Запись только для owner: `PATCH /v1/panel/launcher/release` — multipart с версией и парами "артефакт плюс подпись" по платформам tauri-plugin-updater (windows `NSIS .exe`, linux `.AppImage`, macos `.app.tar.gz`, рядом `.sig`). Публикация инкрементальная: CI-матрица по ОС догружает свои платформы в один релиз, повторная публикация заменяет файлы. Появление релиза в `latest.json` последний шаг: до него клиенты видят прежнюю версию. `latest.json` генерируется на лету из файлов на диске, платформа без подписи не публикуется.

Публикация атомарна по схеме "сначала данные, потом указатель". Сбой посередине откатывает сделанное, а служебные каталоги (`.staging-*`, `.lock-*`, `.old-*`) не раздаются статикой и чистятся сами.

## Обслуживание

- Cron в 04:00 чистит из БД пользователей, удалённых больше 30 дней назад. Файлы скинов и плащей остаются на диске, их можно убирать по своему расписанию.
- Temp-файлы оборванных загрузок и staging-каталоги свипаются при старте сервера. Живой сервер сам свои временные файлы подчищает.
- Версию и релизные каталоги руками не редактировать при работающем сервере: у записи свои атомарные процедуры, ручная правка ломает инвариант "версия есть только если есть файлы".
- Рестарт по кнопке панели это SIGTERM себе с graceful shutdown, pm2 возвращает процесс. Долгий рестарт (аптайм короче 10 секунд при падении) считается падением и ест лимит рестартов, обычный перезапуск живого процесса нет.
